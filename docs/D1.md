# D1 — Migrations From Outside a Worker

`goflare.NewD1Migrator` runs DDL migrations against a Cloudflare D1 database
from CI or a developer machine — outside a Worker, where the
`tinywasm/cloudflare/d1.NewEdge` binding does not exist.

> The D1 **ORM adapter** used *inside* a Worker (`NewEdge`, model setup,
> `wrangler.toml` binding config) lives in `tinywasm/cloudflare`, not here —
> see [that repo's docs/D1.md](https://github.com/tinywasm/cloudflare/blob/main/docs/D1.md).
> This file covers only the host/CI-side migration tooling, which belongs in
> `goflare` per `tinywasm/cloudflare/AGENTS.md` ("no tooling code, ever,
> regardless of build tag").

## Public API

```go
// NewD1Migrator returns a ddl.Execer that runs schema migrations against a
// D1 database from CI or a developer machine.
func NewD1Migrator(accountID, databaseID, apiToken string) (ddl.Execer, error)
```

It builds on `CfClient` (`cloudflare.go`) rather than a second HTTP
implementation — Bearer auth and `{success,errors,result}` envelope parsing
are already correct there. The returned `ddl.Execer` has exactly one method
(`Exec`): no `Query`, no `QueryRow`, nothing to fake.

## Usage

```go
//go:build !wasm

package main

import (
	"github.com/tinywasm/ddl"
	"github.com/tinywasm/goflare"
	"github.com/tinywasm/sqlt"
)

func main() {
	conn, err := goflare.NewD1Migrator(accountID, databaseID, apiToken)
	if err != nil {
		// handle error
	}
	err = ddl.New(conn, sqlt.NewCompiler()).Sync(models...)
}
```

## Behavior

Because `*CfClient` is not a `storage.Conn`, `ddl.Sync` takes its additive
path — `CREATE TABLE` plus `ADD COLUMN`, no safe-drop probe. That is the same
path the WASM `NewEdge` adapter already produces in production (it doesn't
implement `ddl.TableIntrospector` either), so migrating through
`NewD1Migrator` does not change migration behavior versus the edge runtime.

D1's Query API accepts multiple statements joined by `;` as one batch, but
`ddl.Sync` calls `Exec` once per statement — a migration of ~14 models costs
~14 round trips. That is irrelevant in CI (once per deploy); batching would
require buffering `Exec` calls plus a `Flush()` for no measured benefit here.
